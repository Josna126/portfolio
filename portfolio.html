Case studies

Project
Agremate community platform
Role
Product & UI designer and full-stack developer (intern)
Timeline
Jun 2026 to present
Tools
Figma, React.js, Tailwind CSS, Node.js, Anthropic Claude API
Scope
7 modules

Problem

The platform needed seven different features (posts, reviews, ticketing, a vendor marketplace, in-house ads, identity verification and an AI chatbot) that would be used by very different people, yet had to feel like one product.

Users

Community members who post and review, vendors who list services, and admins who handle support. Each has a different goal and a different tolerance for friction.

Process

I mapped the user flow for each module first, sketched low-fidelity wireframes to settle structure and priority, then moved to high-fidelity screens and clickable Figma prototypes. Prototypes went to product and engineering teammates for review before anything was built in React.

Wireframes and screens recreated for this case study. Ticket titles are sample content.

Key decisions

Ticket Manager as a Kanban boardSupport issues are easiest to act on when priority, status and SLA are visible at a glance, so each ticket card carries all three instead of hiding them in a detail page.
Identity and payment as guided stepsAadhaar KYC and Razorpay checkout are high-anxiety moments. I broke them into short steps with a progress indicator and wrote error messages that say what went wrong and how to fix it.
Chatbot with a clear handoffThe AI chatbot answers FAQs and looks up services, but ticket creation runs on deterministic backend logic, so users always know when a real support ticket has been raised.
One set of componentsReusable components and Tailwind tokens for color, type and spacing keep all seven modules consistent and make each new screen faster to build.

Outcome

All seven modules shipped in one consistent interface. The Figma files double as the reference for developers, so design and build stay in step.

What I'd improve next

Run moderated usability sessions on the KYC flow and measure drop-off per step, then use that data to shorten the longest one.

Project
JalDrishti, disease early warning dashboard
Role
UX design, data pipeline and dashboard build
Year
2026
Tools
Figma, Streamlit, Python, scikit-learn, XGBoost, Google Earth Engine

Problem

Waterborne disease outbreaks are usually noticed after people fall sick. Public satellite data can signal risk earlier, but raw model scores mean nothing to a district health officer.

Users

District officials and policymakers who need to decide where to act, often with little time and no data-science background.

2–4 weeksadvance warning of outbreaks
5 layersfrom satellite data to dashboard

Process

I started from the decision the user has to make (which district needs attention first?) and worked backwards to the screen. I wireframed the layout in Figma, tested the information hierarchy against that one question, then built it in Streamlit.

District names and risk levels are sample data used to show the layout.

Key decisions

Alerts by district, not by model outputThe dashboard shows district-level warnings ranked by risk. Probabilities and features stay one layer down for those who want them.
Lead with the actionEach alert opens with what to watch and when, since the 2–4 week lead time is the most useful thing the system offers.

Outcome

A working end-to-end pipeline and an interactive dashboard that turns public satellite data into district-level early warnings.

What I'd improve next

Test the alert wording with actual health officers and check that the risk levels are read the way I intended.

Project
NullBreach, AI-powered security scanner
Role
Interaction design and full-stack build
Year
2026
Tools
Figma, React, Python, Mistral AI, OWASP Top 10

Problem

Security scanners tend to produce long lists of findings, many of them false positives. Developers learn to ignore them, which defeats the purpose.

Users

Developers checking their own web applications against the OWASP Top 10 while they build.

3interfaces: web, API, VS Code
12 agentsin a 6-phase pipeline

Process

I mapped where a developer already works (the editor, the browser, the CI pipeline) and designed one interaction model that carries across all three interfaces, so learning one means knowing the others. Wireframes for the dashboard and results views came first, then a prototype, then the build.

Findings and confidence values are sample data used to show the layout.

Key decisions

Severity and confidence shown togetherA finding shows how serious it is and how sure the scanner is. A confidence-validation step in the pipeline lowers the noise from false positives.
Fix suggestions next to the findingAn LLM suggests a fix beside each issue, so the developer doesn't have to leave the screen to work out what to do.

Outcome

A scanner developers can run from the dashboard, the API or their editor, with the same finding format everywhere.

What I'd improve next

Watch developers use the results view for the first time and find where they hesitate.

How I work

Start with the decision

Before drawing screens, I ask what the user is trying to decide or finish, and design the shortest honest path to it.

Cheap first, polished later

Wireframes and rough prototypes settle structure quickly. Visual polish comes after the flow holds up.

Design for the build

Because I also write the front-end, I use components and tokens that developers can adopt directly, and I know what a state costs to build.

Iterate on feedback

Critiques from designers, PMs and engineers are the fastest way to improve a design, so I share early and change it.
